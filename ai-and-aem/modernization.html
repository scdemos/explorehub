Experience Modernization

Most enterprise EDS projects start with content that already lives in somewhere else: AEM 6.5, AEMaaCS classic, Sitecore, WordPress, custom CMSs. Modernization is the inbound migration story — and where AI shines.

Migration AMS AEMaaCS WCM Modernization

Approach

The honest answer: there's no universal "modernization button." But the demo's page-import skill plus a thoughtful prompt covers ~80% of typical migrations. The remaining 20% — bespoke components, scripted personalization, server-side includes — needs architect-level judgment.

What changes vs a brand-new build:

  • Source is HTML, not a brief. The agent extracts intent from existing markup, not greenfield design.
  • Block selection is constrained. Use what the EDS project already has; flag missing capabilities for explicit decision.
  • Metadata matters more. SEO, social previews, redirects — losing any of these in migration is a real-money cost.
  • Scale is the differentiator. 5 pages = manual review. 5,000 pages = automation with sampled QA.

Migration prompt patterns

Single-page modernization

Modernize this AEM 6.5 page to our EDS site:
  Source: /tmp/legacy-export/products/widget-x.html
  Target: content/products/widget-x.html

Constraints:
- Identify each WCM component used; map to closest EDS block we already have.
- If no block fits, write the section as default content and flag it for review.
- Preserve title, description, og:image, canonical URL.
- Strip legacy analytics tags — we re-add via plugins/martech.
- Remove inline styles. Keep semantic HTML.
- Preserve any data-attributes the editorial team uses for tagging.

Run preview-import after, and surface a diff vs the original page screenshot.

Bulk modernization (sample first, then run)

I need to migrate ~3,400 product pages from /tmp/legacy-products/.

Phase 1 (now): pick 5 representative samples, modernize each, show me diffs and your block mapping decisions. I'll review and approve the mapping rules.

Phase 2 (after approval): apply the same rules to the full set. Output to content/products/. Generate a CSV report with: sourcePath, targetPath, blocksUsed, fallbacksToDefault, anyManualFlags.

Don't run Phase 2 until I confirm Phase 1 is good.

Component inventory before migration

Scan /tmp/legacy-export/. Build an inventory of:
- Every WCM component name used (count by frequency)
- Inline styles or scripts that need replacement
- Custom data attributes
- Image / video paths (and their final hosts)

Output a markdown report I can take to the architecture review.

Mapping legacy components to EDS blocks

Encode the mapping in your project (e.g. .cursor/rules/migration-mappings.mdc) so every migration session uses the same rules:

## WCM → EDS block mapping

- core/wcm/components/text → default content (paragraphs)
- core/wcm/components/title → h1/h2/h3 default content
- core/wcm/components/teaser → blocks/hero (single-image variant)
- core/wcm/components/carousel → blocks/cards (default variant) — MANUAL REVIEW: carousel auto-rotation lost
- core/wcm/components/accordion → blocks/faq
- core/wcm/components/tabs → tabs (section metadata pattern, not a block)
- proj/components/cta-button → button auto-decoration in default content
- proj/components/quote → default content (blockquote)
- proj/components/[unknown] → DEFAULT CONTENT + FLAG for manual review

The agent reads .cursor/rules on every prompt. Once you've encoded the mappings, the modernization prompt becomes one-liner: "Modernize /tmp/legacy-export/widget-x.html using our migration rules."

QA after migration

  • Visual diff sampling. Don't trust a 100% pass rate; sample 1% of migrated pages and visual-diff against the original (Playwright + pixel-diff tool).
  • SEO regression check. Crawl the migrated site, compare H1/title/meta against pre-migration extraction. Set hard thresholds (zero pages with missing <title>, < 1% with title/H1 mismatch).
  • Redirect map. Every URL change needs a redirect from the legacy URL → new URL. Have the agent build this from the migration report.
  • Author UX. Open 10 random migrated pages in DA and confirm authors can edit them without docs. If the block tables are unreadable, your mapping is wrong.
  • CWV. Run Lighthouse on a sample of pages before celebrating. Migration occasionally introduces inline scripts or unoptimized images that tank LCP.

AMS / AEMaaCS specifics

  • Use .html exports, not JCR snapshots. The agent works with rendered HTML — let the legacy stack do the rendering, then migrate the output.
  • Personalization rules don't auto-port. If pages use ContextHub or Adobe Target activities, list them separately and migrate via the experimentation playbook.
  • Servlets / fragments / experience fragments all need explicit decisions: become EDS fragments, become blocks, or become headless API calls.
  • Authoring continuity. Ship a Sidekick / DA bookmark to every legacy author so they don't lose access to their drafts during the cutover window.

Non-AEM legacy stacks

Most of the patterns above transfer. Differences:

  • WordPress: use the WP REST API for the inventory step instead of HTML scraping. Otherwise identical.
  • Drupal: map content types → DA folder structure 1:1; map paragraphs → blocks via the same mapping doc.
  • Custom CMSs: if there's no API, scrape the rendered site. The scrape-webpage skill handles JS-rendered pages.
