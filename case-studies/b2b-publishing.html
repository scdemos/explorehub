B2B publishing

From deploy-to-change homepages to daily editorial on Edge Delivery — taxonomy-driven rails, search at scale, and sibling brands on one platform.

Publishing B2B Migration
Anonymous case study. A composite migration narrative for this industry — useful for planning your own EDS program, not a named customer endorsement.

Overview

A channel-industry publisher ran multiple editorial brands with high article volume. Homepages were rebuilt through CMS workflows that still required engineering for layout changes. Search across archives was slow to evolve; sibling properties duplicated effort on templates and integrations.

The move to EDS made the homepage a composable document: editors arrange rails from blocks, articles publish through standard templates, and query-index powers search and related content across the portfolio.

Where the program started

  • Homepage composition locked in monolithic templates — news cycles waited on deploys.
  • Article metadata inconsistent — related content and facets unreliable.
  • Separate theme implementations per brand property.
  • Syndication and partner feeds bolted on outside the main stack.

Migration journey

  1. Model the article. Standard block table for body content; required metadata (topic, author, date, brand) for index generation.
  2. Rebuild the homepage as sections. Each zone (lead story, trending, sponsored rail) mapped to cards or related-articles blocks.
  3. Generate query-index at publish. Search UI and listing blocks read JSON indexes — no server-side CMS query layer.
  4. Theme sibling brands. Shared block code; section metadata and design tokens differentiate properties.
  5. Add feeds. RSS/JSON outputs from the same content bus — RSS & feeds playbook.
  6. Migrate archives in batches. High-traffic sections first; long tail articles followed with redirect maps.

What landed on EDS

  • Editors refresh homepages multiple times daily without developer involvement.
  • Faceted search and related-articles rails driven by metadata.
  • Multiple brands on shared delivery code with distinct theming.
  • Partner and syndication feeds generated from authored content.

Technical highlights

Homepage assembly

Section-metadata zones and card rails — authors swap stories, not templates.

Related content

Metadata-driven rails — Related articles cookbook.

Search at scale

Client-side search over query-index — Search & discovery.

Multi-brand theming

One repo, token and fragment differences per property.

Target architecture

flowchart LR
  Editors[Editorial authors] --> DA[Document Authoring]
  DA --> EDS[EDS delivery]
  EDS --> Index[query-index.json]
  Index --> Search[Search / listing blocks]
  EDS --> Feeds[RSS / JSON feeds]

Publishing generates indexes and feeds at build time; reader experiences are static-fast at the edge.

Lessons from the journey

  • Metadata is the editorial product. Facets and related rails only work when tags are mandatory, not optional.
  • Homepage is a living document. Treat it like a dashboard of blocks, not a quarterly redesign project.
  • Shared platform, distinct brands. Theming belongs in tokens and fragments — not duplicate block forks.
  • Plan for archive scale. Index size and client search limits matter at tens of thousands of articles.
