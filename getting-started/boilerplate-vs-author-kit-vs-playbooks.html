Boilerplate vs Author Kit vs Playbooks

Three different things that all sound like "starting points." Pick the right one for the right job.

The 30-second answer

  • aem-boilerplate — your project's code starts here. Fork once per site / project.
  • author-kit — your project's authoring tools (Sidekick plugins, DA tools) start here. Imported as a dependency, not forked.
  • This Reference Playbook — your team's brain for "how would I solve this use case." Read it; copy patterns; never fork it.

How they fit together

Imagine a typical project month one:

  1. Day 1 — Fork aem-boilerplate as your project's repo. Configure DA, Sidekick, hosting.
  2. Day 7 — A stakeholder asks for a "tags picker" for content authors. Import the Tags plugin from author-kit instead of building one.
  3. Day 14 — You need to ship gated content. Read the Gated Content playbook, see how scdemos/demo implements it, copy the worker + auth-toggle pattern, adapt to your auth provider.
  4. Day 21 — Marketing wants A/B tests. Read the Experimentation playbook, copy the experimentation plugin pattern, ship it.

You forked once (boilerplate). You imported as needed (author-kit). You inspected and adapted patterns (this playbook). At no point did you take a hard dependency on the playbook itself — and that's the design.

Common confusions, cleared up

"Should I fork scdemos/demo?"

Almost certainly no. scdemos/demo is a reference — a kitchen-sink demo with 60+ blocks across many use cases. Forking it means inheriting all of it, which is rarely what you want. Instead: fork aem-boilerplate, then copy specific blocks / workers / patterns from scdemos/demo as you need them.

"Is author-kit a UI framework?"

No. It's a collection of small, independent tools (Sidekick plugins, DA helpers). You import the ones you need, ignore the ones you don't. There's no shared framework code to take a dependency on.

"Why isn't this Reference Playbook on aem.live?"

Because what's on aem.live is "Adobe-blessed" and goes through the official documentation review process. This playbook trades that for speed and breadth — it covers patterns we've shipped to customers but that haven't been formalized yet. Treat it as community knowledge, not Adobe doctrine.

"Can I contribute back?"

Yes — see Contributing & feedback. New playbook proposals welcome.
