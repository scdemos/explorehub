How to Use Experimentation, Audiences & Campaigns

Complete implementation guide for A/B testing, audience targeting, and campaign personalization

Feature Plugin Advanced

Overview

The AEM Experimentation plugin enables privacy-first A/B testing, audience segmentation, and campaign targeting without requiring code changes. Authors control all configuration through page metadata, and simulation tools provide instant previewing of all variants.

View Live Demo Author Perspective Plugin Repository

Three Core Capabilities

Feature What It Does Triggered By
Experiments A/B test content variants with traffic splitting Automatic (random split)
Audiences Serve content based on user segment (mobile, geo, etc.) Automatic (conditions defined in code)
Campaigns Serve content based on marketing campaigns URL parameter (?campaign= or ?utm_campaign=)

Installation

Step 1: Add Plugin to Project

Add the experimentation plugin as a git subtree:

Terminal 
git subtree add --squash --prefix plugins/experimentation \
  git@github.com:adobe/aem-experimentation.git main

Step 2: Define Audiences

Add audience definitions at the top of scripts/scripts.js:

scripts.js - Audience definitions 
// Define audiences that can be referenced in page metadata
const AUDIENCES = {
  // Device-based audiences
  mobile: () => window.innerWidth < 600,
  desktop: () => window.innerWidth >= 600,

  // Add custom audiences as needed:
  // tablet: () => window.innerWidth >= 600 && window.innerWidth < 900,
  // us: () => navigator.language.startsWith('en-US'),
  // eu: () => ['en-GB', 'fr-FR', 'de-DE'].some(l => navigator.language.startsWith(l)),
  // returning: () => document.cookie.includes('visited=true'),
};
Important: Audiences are defined by developers but referenced by authors. Keep audience names simple and descriptive (e.g., "mobile", "us", "returning").

Step 3: Create Plugin Context

Create a context object that provides required utilities to the plugin:

scripts.js - Plugin context 
import {
  getMetadata,
  loadCSS,
  loadScript,
  sampleRUM,
  toCamelCase,
  toClassName,
} from './aem.js';

import { getAllMetadata } from './shared.js';

function getExperimentationContext() {
  return {
    getAllMetadata,
    getMetadata,
    loadCSS,
    loadScript,
    sampleRUM,
    toCamelCase,
    toClassName,
  };
}

Step 4: Check if Experimentation is Enabled

Create a helper to detect if experimentation features are configured on the current page:

scripts.js - Detection helper 
function isExperimentationEnabled() {
  return getMetadata('experiment')                   // Has experiment metadata
    || Object.keys(getAllMetadata('campaign')).length // Has campaign metadata
    || Object.keys(getAllMetadata('audience')).length; // Has audience metadata
}

Step 5: Load Plugin in Eager Phase

Load the plugin early to avoid content flash. This must happen before content decoration:

scripts.js - Eager phase integration 
async function loadEager(doc) {
  // ... other eager phase code ...

  // Load experimentation plugin EARLY to prevent content flash
  if (isExperimentationEnabled()) {
    const { loadEager: runEager } = await import('../plugins/experimentation/src/index.js');
    await runEager(
      document,
      { audiences: AUDIENCES },      // Pass audience definitions
      getExperimentationContext()    // Pass utility context
    );
  }

  // ... continue with decoration, blocks, etc ...
}

Step 6: Load Overlay in Lazy Phase

Load the simulation overlay after the page content is ready:

scripts.js - Lazy phase integration 
async function loadLazy(doc) {
  // ... other lazy phase code ...

  // Load experimentation overlay (non-blocking, for authoring)
  if (isExperimentationEnabled()) {
    const { loadLazy: runLazy } = await import('../plugins/experimentation/src/index.js');
    await runLazy(
      document,
      { audiences: AUDIENCES },
      getExperimentationContext()
    );
  }
}

Feature 1: Experiments (A/B Testing)

Experiments allow authors to test content variations with random traffic splitting. No code changes required - everything is configured via metadata.

How It Works

  1. Author creates variant pages (duplicates with content changes)
  2. Author adds experiment metadata to control page
  3. Plugin randomly assigns visitors to control or variant
  4. Assignment stored in session storage (no cookies)
  5. RUM tracks performance metrics for each variant

Content Structure

Authors add experiment metadata to the control page:

Metadata Key Value Description
Experiment hero-test Experiment name (used in RUM)
Experiment Variants /variant-1 URL(s) of variant pages (comma-separated)
Experiment Split 30 Variant traffic % (control gets remainder)
Experiment Status Active Active or Inactive
Experiment Start Date 2026-04-01 When experiment begins
Experiment End Date 2026-04-30 When experiment ends

Runtime Access

Access experiment data in JavaScript for analytics integration:

JavaScript API

if (window.hlx.experiment) {
  console.log('Experiment:', window.hlx.experiment.id);

Feature 2: Audiences (Personalization)

Audiences let you serve different content to different user segments automatically - no URL parameters needed.

How It Works

  1. Developer defines audience conditions in scripts.js (e.g., mobile, desktop, geo)
  2. Author creates audience-specific content pages
  3. Author references audience names in metadata
  4. Plugin evaluates conditions on page load
  5. Matching audience page is served automatically

Built-in Audiences

From the installation section, recall these default audiences:

Default audiences (scripts.js) 
const AUDIENCES = {
  mobile: () => window.innerWidth < 600,
  desktop: () => window.innerWidth >= 600,
};

Custom Audience Examples

Advanced Audience Definitions
Custom audiences (scripts.js) 
const AUDIENCES = {
  // Device-based
  mobile: () => window.innerWidth < 600,
  desktop: () => window.innerWidth >= 600,
  tablet: () => window.innerWidth >= 600 && window.innerWidth < 900,

  // Geography-based (simplified - use IP geolocation for production)
  us: () => navigator.language.startsWith('en-US'),
  eu: () => ['en-GB', 'fr-FR', 'de-DE'].some(l => navigator.language.startsWith(l)),

  // Visitor type (requires cookie)
  returning: () => document.cookie.includes('visited=true'),
  new: () => !document.cookie.includes('visited=true'),

  // Connection speed
  slow: () => navigator.connection?.effectiveType === '2g' || navigator.connection?.effectiveType === 'slow-2g',
  fast: () => navigator.connection?.effectiveType === '4g',

  // Time-based
  weekday: () => new Date().getDay() >= 1 && new Date().getDay() <= 5,
  weekend: () => new Date().getDay() === 0 || new Date().getDay() === 6,
};
Privacy Note: Avoid audiences that rely on personal data (cookies, tracking, etc.) unless you have proper consent mechanisms.

Feature 3: Campaigns (Link-Driven Targeting)

Campaigns serve different content based on URL parameters - perfect for email and social campaigns with UTM tracking.

How It Works

  1. Author creates campaign-specific landing pages
  2. Author adds campaign metadata to main page
  3. Marketing appends ?campaign=name or ?utm_campaign=name to links
  4. Plugin checks URL parameters on load
  5. Matching campaign page is served

Content Structure

Metadata Key Value Description
Campaign: Holiday /holiday-landing Campaign name and variant URL
Campaign Audience mobile Optional: restrict to audience

Simulation & Testing

The experimentation overlay provides built-in simulation for all variants:

Overlay Features

  • Experiment View: Shows all variants with traffic splits and "Simulate" links
  • Audience View: Shows all audiences with current match status
  • Campaign View: Shows all campaigns with activation links
  • Direct URLs: Simulation appends URL parameters for easy sharing

Simulation Parameters

Parameter Example Effect
?experiment=variant-name ?experiment=challenger-1 Force specific variant
?audience=name ?audience=mobile Force specific audience
?campaign=name ?campaign=holiday Activate campaign
?utm_campaign=name ?utm_campaign=holiday Activate campaign (UTM)
Pro Tip: Share simulation URLs with stakeholders to preview variants without publishing.

Performance Considerations

Eager Phase Impact

  • Plugin loads early to prevent content flash
  • Adds ~50-100ms to LCP on pages with experimentation
  • Essential trade-off to avoid showing wrong variant
  • Only impacts pages with experimentation metadata

RUM Sampling

The plugin increases RUM sampling for faster data collection:

Default RUM sampling 
// Normal pages: 1% sampling (1 out of 100)
// Experimentation pages: 10% sampling (1 out of 10)
// Higher sampling = faster statistical significance

Session Storage

Variant assignment persists in session storage:

  • No cookies = privacy-compliant
  • Assignment cleared when browser closes
  • Fresh assignment on new session

Common Questions

How does traffic splitting work?

By default, variants split traffic evenly. Control gets remaining percentage.

Example with 3 variants:

  • No split specified: Control 25%, each variant 25%
  • Experiment Split: 20, 30: Control 50%, variant1 20%, variant2 30%
Can I run multiple experiments on one page?

No - only one experiment per page. If testing multiple changes, combine them in variant pages.

When do I see experiment results?

Results flow through RUM. You need:

  • Domain key from aemcs-workspace.adobe.com
  • Sufficient traffic for statistical significance
  • Gear icon in overlay shows inline results
Does this work on production?

Yes! Experiment/audience/campaign logic runs on all environments. The overlay only appears on preview (.aem.page) and localhost.

What happens when an experiment ends?

Remove experiment metadata or set status to Inactive. Promote winning variant content to the main page manually.

Can campaigns trigger automatically?

No - campaigns require URL parameter. For automatic switching based on conditions (geo, device), use audiences instead.
