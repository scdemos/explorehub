Experimentation & personalization

Two layers of decisioning: lightweight in-page A/B + audiences (always-on, no LCP cost), and a deeper Adobe WebSDK / Target integration loaded in a phased way through the MarTech plugin.

A/B Audiences Adobe Target Web SDK RUM

Problem

You need three things, often confused for one: (1) lightweight A/B tests on EDS pages, (2) audience-based content swaps without server roundtrips, (3) Adobe Target personalization and analytics through the WebSDK. Mash them together naively and your LCP collapses. Done right, all three coexist with minimal CWV impact.

Three priority lanes — eager (decisioning that affects the LCP element runs here), lazy (analytics events, propositions display), delayed (anything that's not on the critical path). The MarTech plugin enforces this; you don't write the timing wires by hand.

Code snippets

1. Eager phase — start MarTech, run experiments before decorateMain

scripts/scripts.js (eager) View on GitHub → 
async function loadEager(doc) {
  decorateTemplateAndTheme();
  applyTheme();

  const isConsentGiven = true;
  const martechLoadedPromise = !IS_QUICK_EDIT && initMartech(
    {
      datastreamId: 'd73be188-...-8aa7cd1e343b',
      orgId: '138A07885EE042D20A495CFA@AdobeOrg',
      defaultConsent: 'in',
      edgeConfigOverrides: {
        com_adobe_target: { propertyToken: '2375354b-...-7c38fccd590b' },
      },
    },
    {
      personalization: !!getMetadata('target') && isConsentGiven,
      launchUrls: ['https://assets.adobedtm.com/.../launch-452113bfea88.min.js'],
      decisionScopes: ['homepage-hero-mbox', 'homepage-teaser-mbox'],
      propositionMetadata: {
        'homepage-hero-mbox': { selector: 'main .section:first-child', actionType: 'replaceHtml' },
        'homepage-teaser-mbox': { selector: 'main .section:nth-child(2)', actionType: 'replaceHtml' },
      },
    },
  );

  const main = doc.querySelector('main');
  if (main) {
    if (isExperimentationEnabled()) {
      const { loadEager: runEager } = await import('../plugins/experimentation/src/index.js');
      await runEager(document, { audiences: AUDIENCES }, getExperimentationContext());
    }
    decorateMain(main);
    document.body.classList.add('appear');
    await Promise.all([
      martechLoadedPromise && martechLoadedPromise.then(martechEager),
      loadSection(main.querySelector('.section'), async (s) => {
        await waitForFirstImage(s);
        await loadFragments(s);
      }),
    ]);
  }
}

2. Experimentation triggers — page metadata only

scripts/scripts.js (gate) View on GitHub → 
function isExperimentationEnabled() {
  return getMetadata('experiment')
    || Object.keys(getAllMetadata('campaign')).length
    || Object.keys(getAllMetadata('audience')).length;
}

const AUDIENCES = {
  mobile: () => window.innerWidth < 600,
  desktop: () => window.innerWidth >= 600,
};

The plugins/experimentation code path only loads when the page declares experiment, campaign:*, or audience-* meta tags. Pages with no experiment pay zero JS cost.

3. Lazy phase — WebSDK send-event after content settles

scripts/scripts.js (lazy) View on GitHub → 
async function loadLazy(doc) {
  // ... header / fragments / sections ...
  loadFooter(footerEl);
  if (!IS_QUICK_EDIT) await martechLazy();
  // martechLazy fires the WebSDK event for the page-view, applies any
  // remaining propositions that weren't on the LCP path.
}

4. Delayed phase — anything off the critical path

scripts/delayed.js ends with martechDelayed(). Use this for non-critical telemetry, third-party tags, conversion-tracking pixels.

Notes & gotchas

  • LCP is the budget. The MarTech init starts before decorateMain but martechEager() only resolves after the WebSDK is ready. The page never blocks on it — it's parallel to loadSection(firstSection).
  • Decision scopes are mboxes. Each decisionScopes entry maps to an mbox in Target. The propositionMetadata tells the plugin where in the DOM to apply the proposition (selector + actionType). Use this for hero swaps, teaser swaps, "show this badge to mobile users" — anything authored as plain HTML.
  • Quick Edit bypass. The plugin guards on IS_QUICK_EDIT. Don't run experiments inside the DA quick-edit overlay — authors get a stable view to edit.
  • Consent stub vs reality. The demo hardcodes isConsentGiven = true. Replace with your actual CMP signal (tcfapi, OneTrust, or in-house). Without that, regional compliance breaks.
  • Audiences first, experiments second. Audiences are stable URL-driven matches (mobile/desktop, locale, logged-in) — they should be in the eager path. Bucket-based experiments are randomized; use them for tactical UI tests, not core layout decisions.
  • RUM hooks. The experimentation plugin samples RUM events with the variant id, so dashboards can split CWV by experiment. Don't disable sampleRUM — it's how you discover that variant B tanked LCP.
  • Avoid CLS during proposition apply. When Target replaces the first section's HTML, set min-height on the LCP container in your CSS so the layout doesn't shift when the proposition lands.

How to adapt into my project

  1. Choose the layer you need. Most projects only need the experimentation plugin (no Target). Start there. Layer the WebSDK in only when marketing wants Target / Analytics integration.
  2. Copy plugins/experimentation + plugins/martech as starting points. They're versioned plugins, not bespoke code — keep the upstream remote configured so you can pull updates.
  3. Update the MarTech config. Replace datastreamId, orgId, and propertyToken with your tenant's values from Adobe Experience Platform.
  4. Wire isExperimentationEnabled() from loadEager exactly as the demo does. Don't load the plugin unconditionally.
  5. Author one experiment end-to-end on a low-stakes page first. Add the meta, deploy, verify ?experiment=... control vs treatment switch, confirm RUM signals.
  6. Add CMP integration before going live. Replace isConsentGiven = true with the real signal.
