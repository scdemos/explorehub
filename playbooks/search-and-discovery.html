Search & discovery

Faceted search and content recommendations using only query-index.json. No Algolia, no Elasticsearch, no external service. The same data also powers related-content surfaces and recommendations.

Search Query Index Discovery Recommendations

Problem

Customers want a search bar with filters and pagination, plus "related content" rails on article pages. The team has been told search needs Algolia, but the content set is small (hundreds, not millions) and authors don't want to maintain a parallel taxonomy in a separate dashboard.

One JSON, three consumers. query-index.json is published from a spreadsheet that captures every page's title, description, image, keywords, date, lastModified, and template. Anything that needs to surface content reads from this index — no parallel store.

Code snippets

1. Paginated query-index fetch (shared utility)

scripts/shared.js View on GitHub → 
export const QUERY_INDEX_PAGE_SIZE = 500;

export async function fetchQueryIndexPage(offset, limit, baseUrl = '') {
  const path = `/query-index.json?offset=${offset}&limit=${limit}`;
  const url = baseUrl ? `${String(baseUrl).replace(/\/+$/, '')}${path}` : path;
  const resp = await fetch(url);
  if (!resp.ok) throw new Error(`Query index request failed: ${resp.status}`);
  return (await resp.json())?.data || [];
}

export async function fetchQueryIndexAll(options = {}) {
  const { pageSize = QUERY_INDEX_PAGE_SIZE, baseUrl = '' } = options;
  async function fetchPage(offset, acc) {
    const rows = await fetchQueryIndexPage(offset, pageSize, baseUrl);
    if (!rows.length) return acc;
    const next = [...acc, ...rows];
    return rows.length === pageSize ? fetchPage(offset + rows.length, next) : next;
  }
  return fetchPage(0, []);
}

2. Search block — facets from authored config

The search block reads its filter groups straight from the block table. Each non-reserved key becomes a facet group, each comma-separated value an option:

blocks/search/search.js (excerpt) View on GitHub → 
const RESERVED_CONFIG_KEYS = ['view', 'keywords', 'excluded-keywords', 'searchbar'];

function parseFilterGroupsFromConfig(config) {
  return Object.entries(config)
    .filter(([key]) => !RESERVED_CONFIG_KEYS.includes(key))
    .map(([key, value]) => {
      const options = String(value || '')
        .split(',').map((v) => v.trim()).filter(Boolean)
        .map((v) => ({ key: toClassName(v), label: v, match: v.toLowerCase() }));
      if (!options.length) return null;
      const label = key.charAt(0).toUpperCase() + key.slice(1).replace(/-/g, ' ');
      return { key, label, options };
    })
    .filter(Boolean);
}

function rowMatchesFilterGroups(row, selectedByGroup, filterGroups) {
  return filterGroups.every((group) => {
    const selected = selectedByGroup.get(group.key) || [];
    if (!selected.length) return true;
    const values = getGroupMatches(row, group);
    return selected.some((v) => values.includes(v));
  });
}

3. Related articles — keyword + recency

blocks/related-articles/related-articles.js (excerpt) View on GitHub → 
function matchArticles(rows, keywordsConfig, excludedConfig, limit) {
  const requested = parseKeywords(keywordsConfig);
  const excluded = parseKeywords(excludedConfig);
  const isRandom = requested.includes('random');
  const hasMultipleKeywords = requested.filter((k) => k !== 'random').length > 1;
  const shouldShuffle = isRandom || hasMultipleKeywords;

  const filtered = isRandom || !requested.length
    ? rows
    : rows.filter((row) => requested.some((k) => rowMatchesKeyword(row, k)));

  const withoutExcluded = excluded.length
    ? filtered.filter((row) => !excluded.some((k) => rowMatchesKeyword(row, k)))
    : filtered;

  const deduped = withoutExcluded.filter((row, idx, arr) =>
    arr.findIndex((x) => x.path === row.path) === idx);

  if (shouldShuffle) return shuffle(deduped).slice(0, limit);
  return deduped.sort((a, b) => getContentTimestamp(b) - getContentTimestamp(a)).slice(0, limit);
}

Three modes from one helper: keyword-matched (recency-sorted), random (shuffled), or curated (authored anchor list joined with index metadata via resolveArticlesFromIndex).

4. Resolving authored links to index metadata

scripts/shared.js (excerpt) View on GitHub → 
export function resolveArticlesFromIndex(authoredLinks, indexRows) {
  return authoredLinks.map(({ path, title: linkTitle }) => {
    const norm = normalizePath(path);
    const row = indexRows.find((r) => r?.path && normalizePath(r.path) === norm);
    const fallbackTitle = norm.split('/').filter(Boolean).pop()?.replace(/-/g, ' ') || norm;
    return {
      path: norm,
      title: row?.title?.trim() || linkTitle || fallbackTitle,
      description: row?.description?.trim() || '',
      image: row?.image,
      date: row?.date || row?.publisheddate || row?.lastModified,
    };
  });
}

Authors paste a bullet list of links into a cards (links) or related-articles block; the block enriches each link with current title/description/image from the index. Authors edit content once, in the page metadata.

Notes & gotchas

  • The index is a contract. Decide your column set early (title, description, image, date, keywords, template, ...). Add columns in the published spreadsheet first, then update the consuming blocks.
  • Comma-separated keywords. The search and related-articles blocks both rely on keywords being a comma list. Spaces are tolerated; case is normalised. Don't store JSON arrays — the existing helpers split on ,.
  • Pagination matters past 500 rows. fetchQueryIndexAll handles it, but the search block uses fetchQueryIndexPage with a fixed FETCH_LIMIT = 500 in the demo. For large catalogs, raise the limit or paginate server-side.
  • Recency sort needs a real date column. If date is empty, the helper falls back to publisheddate then lastModified. Without any of those, sort order is undefined.
  • Filtering is in-browser. Good for < 5k rows. Past that, consider serving a slimmed JSON variant (worker + KV) or moving to a real search index. The blocks are designed so you can swap the data source without touching the UI.
  • "Random" is not stable. If your QA runs flaky tests on a related-articles block configured with keywords: random, mock Math.random or pin the keywords during tests.
  • Search bar UX. The search block treats ?q=... in the URL as the initial query — share-able links, browser history, deep linking from email campaigns. Worth keeping when you customize the block.

How to adapt into my project

  1. Audit your query-index.json — open https://main--<repo>--<org>.aem.live/query-index.json and confirm you have title, description, image, date, keywords at minimum.
  2. Copy scripts/shared.js helpers (fetchQueryIndexAll, parseKeywords, resolveArticlesFromIndex, shuffle). They're project-agnostic.
  3. Pick the variant.
    • Faceted browse → blocks/search.
    • Per-article rail → blocks/related-articles.
    • Curated link list with metadata → blocks/cards (links variant).
  4. Author the block. The blocks/search table accepts arbitrary facet keys — make them match the columns in your index spreadsheet.
  5. Outgrowing in-browser? Keep the same blocks but swap the data layer to a worker that wraps Vectorize / KV / Algolia. The block doesn't care where the JSON came from.
