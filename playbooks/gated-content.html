Gated content

Member-only sections, blocks, and pages on EDS — without owning a session store. Cloudflare Access does the auth, the CDN worker rewrites the HTML, and an author-only toggle lets editors preview either state.

Auth Workers CDN Cloudflare Access

Problem

You need parts of a public site to be visible only to authenticated users — paywalled articles, partner portals, members-only sections inside a marketing page. EDS has no concept of a session, and the project doesn't justify a full identity provider in front of every page. You also need authors to preview the gated and ungated views without logging in and out.

Three layers: authoring (page meta + section metadata), auth (Cloudflare Access in front of some routes), CDN rewrite (a Cloudflare Worker that strips gated sections per the auth state). A separate scripts/utils/gated-content.js mirrors the same rewrite client-side so authors can preview both views in aem.page.

Code snippets

The page is gated when <meta name="gated" content="true"> is present. Sections opt into a specific audience via data-view or section-metadata view: logged-in or logged-out.

1. CDN worker rewrites HTML by audience

workers/cdn/handlers/gating.js View on GitHub → 
const GATED_META = /<meta[^>]+name=["']gated["'][^>]*content=["']true["']/i;

function transformGatedHtml(html, loggedIn) {
  const $ = load(html);
  const removeEls = new Set();
  $('main > div').each((_, el) => {
    const aud = audience($, $(el));
    if (aud) {
      const drop = (loggedIn && aud === 'logged-out') || (!loggedIn && aud === 'logged-in');
      if (drop) removeEls.add(el);
    }
    if (!removeEls.has(el)) {
      // Block-level: strip .logged-in / .logged-out blocks per state
      if (loggedIn) $(el).find('[class*="logged-out"]').remove();
      else $(el).find('[class*="logged-in"]').remove();
    }
  });
  removeEls.forEach((node) => $(node).remove());
  return $.html();
}

export async function applyGatingIfNeeded(request, requestURL, response) {
  if (request.method !== 'GET' || response.status !== 200) return response;
  if (!(response.headers.get('content-type') || '').includes('text/html')) return response;
  const html = await response.text();
  if (!GATED_META.test(html)) return htmlResponse(html, response);
  const out = transformGatedHtml(html, isAuthenticated(request));
  return htmlResponse(out, response, out !== html);
}

Personalised responses get tightened cache + Vary: Cookie automatically by htmlResponse(..., personalized=true).

2. isAuthenticated reads Cloudflare Access headers

workers/cdn/handlers/auth-check.js View on GitHub → 
// CF Access populates these on every request behind an Access policy.
// Cf-Access-Authenticated-User-Email is set after a successful Access login.
export function isAuthenticated(request) {
  return Boolean(
    request.headers.get('Cf-Access-Authenticated-User-Email')
    || request.headers.get('Cf-Access-Jwt-Assertion'),
  );
}

if (pathname === '/auth/session') return json(request, { ...access });

// Mirrors the worker's `audience()`. Runs only in author / preview environments.
function isAuthorEnvironment() {
  const host = window.location.hostname;
  return host.includes('localhost')

    || host.includes('aem.reviews')
    || host.endsWith('.ue.da.live')

Notes & gotchas

  • The CDN worker is the trust boundary. The browser-side applyContentProtection() only runs in aem.page / localhost, so authors can preview. Don't rely on it for production gating — it lives in the page that the user already received.
  • Cache + cookies. When the worker rewrites the HTML for a logged-in user it forces Cache-Control: private, no-cache, must-revalidate and merges Vary: Cookie. Without this you'll serve a logged-in user's HTML to the next anonymous visitor on a shared cache.
  • Two opt-in mechanisms. A whole section is gated via section-metadata view: logged-in (becomes data-view on main > div). A single block is gated by adding the logged-in or logged-out class to the block (e.g. cards (logged-in) in a DA / Word block table).
  • Skip list for fragments. The handler skips /fragments/, /nav.plain.html, and /footer.plain.html. Otherwise you'd risk gating a shared header/footer that's pulled into every page.
  • Cloudflare Access policy scope. Put the Access policy on routes that require a logged-in user (e.g. /account/*). Public pages with mixed gated sections don't need a policy — the worker just reads whatever Access headers happen to be present.
  • Author preview gotcha. Authors edit on aem.page (which never has Cloudflare Access in front), so they always look anonymous to the worker. The toggle bypasses this by toggling ?auth=true and letting the JS layer do the rewrite locally.

How to adapt into my project

  1. Pick your auth provider. The pattern is "trust a header from the edge." Cloudflare Access is the simplest, but Auth0, Okta, or your own JWT-bearing reverse proxy work too — just have isAuthenticated() read the right header.
  2. Copy workers/cdn + workers/auth into your repo. Update ORIGIN_HOSTNAME in workers/cdn/wrangler.jsonc to main--<your-repo>--<your-org>.aem.live.
  3. Decide your audience taxonomy. The demo uses a binary logged-in / logged-out. If you need roles (member, editor, admin), extend audience() to return any string and have the worker compare against a roles claim.
  4. Wire scripts/utils/gated-content.js from scripts/scripts.js's loadLazy. The toggle and section stripping are gated on isGatedPage() — if you forget the gated meta, both layers are no-ops.
  5. Author one gated page end-to-end: add the page meta, mark one section view: logged-in, deploy. Verify in DevTools that main > div[data-view="logged-in"] is missing on the public page and present after ?auth=true.

Don't: bake business secrets into the page and rely on the rewrite to remove them. The pre-rewrite HTML lives at main--<repo>--<org>.aem.live and is publicly fetchable. Fetch privileged data after auth, from a worker that checks the Access header itself.
